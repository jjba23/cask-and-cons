*My work macOS dotfiles.*

~cask-and-cons~ provides a convenience CLI tool (~caco~). Naming stems from a pun on Homebrew casks of macOS and the cons cells of Lisp.

------------------

* My declarative dotfiles in Lisp

Every piece of configuration this tool manages (Git config, gitignore
globals, and others) is expressed as Lisp ( Scheme ) source code and data, alists and other simple constructs,
describing the desired end state, rather than as a series of imperative shell commands that mutate files in place.

#+BEGIN_EXPORT html
<img src="https://jointhefreeworld.org/static-assets/cask-and-cons/finder-icon.png" alt="Finder logo" width="250px" style="max-width: 250px; height: auto;" />
#+END_EXPORT

This is a deliberate choice, as it offers:

- *Reproducibility* — Given the same source (this repo) and the same   inputs (=user-settings.scm= and any local overrides), running =caco install-git= always produces byte-identical output. There is no implicit dependency on whatever state the file happened to be in before, so *re-provisioning a machine (or recovering a wiped one) is just "clone the repo and run the tasks"*.
- *Idempotency* — Install tasks overwrite the target file wholesale instead of patching/appending to it, so running them twice, or after manually editing the config, converges back to the declared state
  instead of accumulating drift or duplicate entries.
- *Auditability* — The desired configuration lives as data in version control, so changes show up as regular, reviewable diffs instead of being buried in shell history or one-off commands you may forget you ran.
- *Separation of data and mechanism* — The "what" (e.g. =gitconfig=,  =gitconfig-personal=) is decoupled from the "how" (the serialization  helpers in =prelude.scm=), so adding a new dotfile module mostly means writing a new data definition, not new file-mutation logic.
- *Portability of machine-specific tweaks* — =load-local-overrides= lets a given machine layer small, local changes on top of the shared declarative base, without forking the repo's own definitions.

* WezTerm

WezTerm is declared in =src/cask-and-cons/brew.scm= (=caco install-brew= installs
it), and unlike iTerm2 it is configured from Lisp rather than by hand:

#+begin_src shell
caco install-wezterm
#+end_src

writes =~/.config/wezterm/wezterm.lua=, generated from
=src/cask-and-cons/wezterm.scm=. Everything the iTerm2 setup above asks you to
click through - the Meta key, 100k lines of scrollback, the transparency and the
blur - is a value in that module (=wezterm-font-family=, =wezterm-scrollback-lines=,
=wezterm-window-opacity=, =wezterm-window-blur=), and the font and the colours are
the ones the Emacs bridge gives Heks Emacs (=Intel One Mono=, =ayu-dark=).

Two keyboard settings replace the iTerm2 clicking outright. Option is not Meta on
macOS by default - it composes characters, so =M-v= types a mathematical symbol
instead of paging - so the generated file turns
off =send_composed_key_when_left_alt_is_pressed= and
=send_composed_key_when_right_alt_is_pressed=, and Option reaches the application
as ESC. =enable_kitty_keyboard= lets a program that asks for the kitty keyboard
protocol (Emacs does) tell chords apart that the legacy encoding cannot, such as
=C-i= against =TAB=.

The window keeps its title bar and its resize border: the generated file asks for
=window_decorations = 'TITLE | RESIZE'=, so macOS draws the native title bar with
its traffic lights and moving, closing and resizing all work the way they always
did. Tabs still exist, but the tab bar stays hidden while there is only one tab.

The value is shared with the Linux twin, and it is also the default value of
=WindowDecorations=, which is what makes it the right one on Wayland: the default
asks the compositor to follow the server's decorations, while any non-default
value (=RESIZE=, =TITLE= alone, anything with =INTEGRATED_BUTTONS=) makes WezTerm
paint a client-side frame of its own -- on the Linux side of this pair that frame
is a 33 pixel band of flat dark with no title and no buttons in it.

The key bindings are the Emacs ones, and they are *guarded*: WezTerm asks each
pane which process is in front of it, and while the answer is one of
=wezterm-yield-apps= - Emacs above all, but also =less=, the editors, the
full-screen TUIs, the multiplexers and the REPLs - the chord is handed straight
back to that application. Inside Emacs =C-x= is Emacs's =C-x=; at a shell prompt it
is the prefix of the terminal's window commands. =C-c= is never bound, because it
is the interrupt signal.

The guard is what lets the terminal claim the page keys at all: =C-v= pages the
scrollback forward and =M-v= pages it back, and inside Emacs or the pager those
same chords are handed over untouched, so the pager keeps its =forw-screen= and
=back-screen= (see [[*The pager][The pager]]) and Emacs keeps its =scroll-up-command=.
WezTerm's own bare-modifier defaults are re-registered through the same guard -
=C-Tab=, =C-S-Tab=, =C-PageUp=, =C-PageDown=, =M-Enter= and =C-Insert= - so a
full-screen program receives them instead of the terminal.

| Chord                     | WezTerm does                       | Emacs equivalent                |
|---------------------------+------------------------------------+---------------------------------|
| =C-x 2=                   | split the pane below               | =C-x 2= split-window-below      |
| =C-x 3=                   | split the pane to the right        | =C-x 3= split-window-right      |
| =C-x 1=                   | zoom the pane in place             | =C-x 1= delete-other-windows    |
| =C-x 0=                   | close the pane                     | =C-x 0= delete-window           |
| =C-x o=                   | move to the next pane              | =C-x o= other-window            |
| =C-x b=                   | pick a pane by name                | =C-x b= switch-to-buffer        |
| =C-x <left> / <right>=    | previous / next tab                | =C-x <left>= previous-buffer    |
| =C-x g=                   | leave the prefix                   | =C-g= keyboard-quit             |
| =S-<arrow>=               | move to the pane in that direction | =S-<arrow>= windmove            |
| =C-y= / =M-w=             | paste / copy                       | =C-y= yank, =M-w= kill-ring-save |
| =C-=, =C--, =C-0=        | grow / shrink / reset the font     | =C-=, =C--= text-scale          |
| =M-s=                     | search the scrollback              | =M-s= search prefix             |
| =C-v= / =M-v=             | page the scrollback down / up      | =C-v= / =M-v= scroll-up-command |
| =S-PageUp= / =S-PageDown= | page the scrollback                | =S-PageUp= scroll-other-window  |
| =S-Home= / =S-End=        | top / bottom of the scrollback     |                                 |

That list is what the terminal does when no application owns the keyboard; while
Emacs, =less= or any other entry of =wezterm-yield-apps= is in front, every one of
these chords goes to it instead. The guard needs
=pane:get_foreground_process_name()=, which only answers for local panes, so over
=ssh= or inside the WezTerm multiplexer the terminal keeps its own binding - and
that is why the scrollback also stays on =S-PageUp= and =S-PageDown=.

As with the other install targets, a machine-specific override can be dropped at
=$XDG_CONFIG_HOME/cask-and-cons/wezterm-settings.scm= (defaulting to
=~/.config/cask-and-cons/wezterm-settings.scm=) to tweak the parameters before the
file is rendered. WezTerm reloads the generated file on its own.

* The =cask-and-cons= CLI

This repo ships its own executable entrypoint, =caco=, a plain bash script that executes =guile=, with =./src= added to the
load path, and hands off to the Scheme entrypoint defined in =src/cask-and-cons/main.scm=, which dispatches to a sub-task based on the CLI arguments.

#+begin_src shell
caco <task> [args...]
#+end_src

=caco --list= is a special-cased alias for =caco list=;

Once the zsh configuration is installed (=./caco install-zsh=), =caco= is also available as a shell function in every directory. It automatically does a =cd ~/Hacking/cask-and-cons= and then runs =./caco "$@"=, so you never need to navigate to the repo or prefix the command with =./= yourself. Note that this leaves your shell in the repo directory afterwards.

Available tasks:

- =list= — print all available tasks
- =compile= — byte-compile every =.scm= file under =src/= with =guild compile -W3=
- =install-brew= — ensure the Homebrew taps, formulae and casks declared in =src/cask-and-cons/brew.scm= are installed (skips what is already present)
- =install-git= — install the Git configuration
- =install-omniwm= — install the OmniWM configuration
- =install-emacs-bridge= — install the settings Heks Emacs reads (=~/.emacs.d/cask-and-cons-bridge.el=)
- =install-zsh= — install the ZSH configuration (=~/.zshrc= and the pager keymap)
- =install-wezterm= — install the WezTerm configuration (=~/.config/wezterm/wezterm.lua=)
- =install-macos= — converge macOS system preferences (Dock, Finder, trackpad, clock, ...) declared in =src/cask-and-cons/macos.scm=; only changed keys are written and only affected processes (Dock, Finder) restart. Override with =~/.config/cask-and-cons/macos-settings.scm=, e.g. =(macos-settings (append (macos-settings) '(("com.apple.dock" (tilesize . 36)))))=

Install targets are just plain tasks named =install-<target>=; there is no separate =install= sub-command or target argument to parse.

#+begin_src shell
caco list
caco --list
caco compile
caco install-git
#+end_src

*** Composing tasks

Tasks that take no arguments can be chained in a single invocation by joining their names with commas (no spaces):

#+begin_src shell
caco compile,install-git
#+end_src

This runs each task in order. Tasks that require their own arguments are not supported inside a chain and must be run on their own.

All tasks log their progress with colored, timestamped output via =log-info=, =log-warning=, =log-error= and =log-success=, exported from
=(cask-and-cons prelude)=.

*** Adding a new install target

All tasks, including install targets, live in the single =%tasks= alist inside =src/cask-and-cons/main.scm=, mapping a task name to a thunk:

#+begin_src scheme
(define %tasks
  `(("compile"     . ,(lambda (args) (compile)))
    ("install-git" . ,(lambda (args) (install-git-config)))
    ("list"        . ,(lambda (args) ...))))
#+end_src

To wire up a new module (e.g. a =waybar= module):

- Implement an =install-waybar-config= function in a new  =src/cask-and-cons/waybar.scm= module, following the pattern in  =src/cask-and-cons/git.scm=.
- =use-module= it at the top of =src/cask-and-cons/main.scm=.
- Add =("install-waybar" . ,(lambda (args) (install-waybar-config)))=
   to =%tasks=.

No changes to the dispatch logic itself are needed.

* ZSH configuration

Install ZSH autosuggestion

#+begin_src shell
git clone https://github.com/jumbojett/zsh-autosuggestions-plugin.git ~/.zsh/zsh-autosuggestions
#+end_src

My ZSH config is managed by the =cask-and-cons= CLI rather than being inlined here. Its source of truth lives in =src/cask-and-cons/zsh.scm=: the machine identity (=zsh-identity=), =setopt= flags and aliases are plain Scheme alists (=zsh-completion-setopts=, =zsh-shell-setopts=, =zsh-history-setopts=, =zsh-aliases=) that get serialized into the final =~/.zshrc= contents, and everything else follows the same install pattern as the Git configuration.

The procedural half of the shell (prompt engine, git segment, helper
functions, greeting pool) lives in =src/cask-and-cons/shell-lib.zsh= and is
spliced verbatim into =~/.zshrc=. It is the zsh twin of
=heks-bash/src/heks-bash/shell-lib.bash= and of the shared block in
=wolk-jjba/home/bash/bashrc.sh=: same two-line prompt, same colours, same
helpers, so all my machines feel like one shell.

#+begin_src shell
╭─ joe@macbook ⌘ macos …/Hacking/cask-and-cons
╰─ main ✚2 ↑1↓3 ⚑1 ⌘
#+end_src

The only differences between machines are the five =CC_*= variables in
=zsh-identity= — flavour name, at-a-glance badge (=macos= here, =guix/linux=
on the desktop, =guix/server= on the server), prompt sigil (=⌘=, =λ=, =ω=),
256-colour accent, and the rc file =reload= re-sources. The prompt shows the
branch (or =@sha= when detached), changed files (=✚n=), conflicts (=✖n=),
clean state (=✓=), =↑n=/=↓n= against the upstream and =⚑n= stashes, from a
single =git status --porcelain=v2 --branch= per prompt.

Handy additions on top of the usual aliases: =about= (machine identity and
prompt legend), =hist-top=, =rc-time=, =mkcd=, =up=, =extract=, =serve=,
=psg=, =kport=, =ports=, =notify= (native macOS notification), =bak=,
=calc=, =json=, =paths=, =ff=, =cdroot=, =reload=, the git shortcuts
(=gst=, =gd=, =gds=, =glog=, =gco=, =gsw=, =gbr=, =gcm=, =gpl=, =gpu=,
=gfetch=), plus =brewu=, =flushdns=, =showfiles= and =hidefiles= for macOS.

*** The pager

=less= is the pager, with Emacs key bindings, exactly as on the Guix
desktop and the Guix server: =src/cask-and-cons/lesskey= (byte-identical
with =heks-bash/src/heks-bash/lesskey= and =wolk-jjba/home/bash/lesskey=)
is installed as =$XDG_CONFIG_HOME/lesskey=, the first place =less= 582 and
later look, so =man=, =git=, =journalctl= and every other pager user share
one set of keys. =PAGER= and =MANPAGER= are =less=, =LESS= is
=-F -I -M -R=.

| Key          | What it does                                   |
|--------------+------------------------------------------------|
| =C-n= =C-p=  | one line down / up                             |
| =C-f= =C-b=  | one screen down / up                           |
| =C-v= =M-v=  | one screen down / up                           |
| =C-d= =C-u=  | half a screen down / up                        |
| =C-a= =C-e=  | top / bottom of the file                       |
| =M-<= =M->=  | top / bottom of the file                       |
| =C-s= =C-r=  | search forward / backward                      |
| =M-g=        | go to line                                     |
| =M-u=        | clear the search highlighting                  |
| =C-l=        | redraw the screen                              |

Inside the =less= prompts the keys are Emacs keys too (=C-a= / =C-e=,
=C-b= / =C-f=, =M-b= / =M-f=, =C-w= / =M-d=, =C-k= / =C-u=, =C-g=), and
nothing was taken away: =space=, =b=, =j=, =k=, =g=, =G=, =/=, =?=, =n=,
=N=, =m=, ='=, =!=, =|= and =q= keep their less meaning. =pager-keys=
prints the map anywhere. =cc_boot= also runs =stty -ixon=, so =C-s= is
forward-search in zle instead of a frozen terminal.

#+begin_src shell
caco install-zsh
#+end_src

This writes =~/.zshrc= and =$XDG_CONFIG_HOME/lesskey=.

** Notes from the terminal: =n=

The notes of the Emacs setup (see the [[https://codeberg.org/jjba23/heks-emacs/src/branch/trunk/docs/notes.org][heks-emacs notes guide]]) are plain files, so the basics work from ZSH when Emacs is not at hand. One command, =n=, installed with the rest of the ZSH configuration, reads and writes exactly the same files in exactly the same formats (so the two never disagree); it uses =fzf= for the pickers when it is installed, and plain prompts otherwise.

#+begin_src sh
echo "try the transducer version" | n capture -t engineering/ideas -T "Transducers"
n todo "email the landlord"       # into the inbox of todo.org
n today                           # birthdays, habits due, the inbox
n find kubernetes                 # pick a note by title and open it
n search "rolling update"         # search the text, jump to the line
n bookmark add                    # the clipboard URL, title fetched, pick a category
n index                           # regenerate every topic's index.org
#+end_src

How it is wired:

- =src/cask-and-cons/notes.zsh= is plain zsh; =zsh.scm= splices it into =~/.zshrc= after the shared library, with =export NOTES_DIR=…=.
- The notes directory is defined once, as =notes-directory= in =user-settings.scm=; the Emacs bridge takes =heks/notes-dir= from the same value.
- The index pages it writes are byte-identical to the ones Emacs writes.

Everything -- every command, how the pickers behave, the file formats the two sides share, recipes, how to test changes on a copy of your notes, limits and troubleshooting -- is in *[[file:docs/notes-from-the-terminal.org][docs/notes-from-the-terminal.org]]*. Moving a note is deliberately left to Emacs, because it has to repair the links that point at it. Run =caco install-zsh= and open a new shell to get it.
