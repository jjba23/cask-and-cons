# Vision

`cask-and-cons` is the description of one macOS machine, written as Scheme data and converged onto it by a chain of tasks. Its subject is not dotfiles but the distance between a declared end state and whatever the machine currently is: a module is a data definition, `prelude.scm` turns it into a file of the right format, and the file is written from scratch so a second run changes nothing and a wiped machine is a clone, a bootstrap and one command away from the first. This document is about where that idea should go next — from a working set of install targets into a provisioner that can be compared against its machine, and can prove that it converged.

It is a personal repository and it reads like one: the values in it are one person's font, one person's signing key, one person's `CDPATH`, one person's two local models. That is not an obstacle to what follows, it is the premise. A configuration honest about being one machine's is the only kind that can be pushed further than a template can.

## Where cask-and-cons is today

The command line is [maak](https://codeberg.org/jjba23/maak), and `maak.scm` at the root is the whole of it: every task is a procedure exported from that module, each a thin wrapper over a module in `src/cask-and-cons/`, and `maak -l` prints them with their docstrings. Tasks that take no arguments chain with commas. There is no bespoke CLI any more — `main.scm` and the `caco` bash script are gone.

The one step maak cannot do is install itself. `./bootstrap` reads `flake.nix` and installs the `caco-tools` Nix profile, which carries maak, sift, araneola, ggg, iter-vitae, lenkesamler and mutastructura from `nix-jointhefreeworld`, plus `just`, `shellcheck`, `delta`, `bash-language-server`, `yaml-language-server`, `vscode-langservers-extracted`, `nil` and `marksman` from nixpkgs. The flake fetches the jointhefreeworld input over `git+https` rather than `github:`, because the latter goes through the GitHub API and rate-limits unauthenticated clients. `caco` survives as a convenience: `install-zsh` writes a shell function that is `maak -C ~/Hacking/cask-and-cons "$@"`, so it works from any directory and leaves the shell where it was.

There are seventeen `.scm` modules in `src/cask-and-cons/`, fifteen of them payloads, and `install-tasks` in `maak.scm` orders sixteen install targets — `brew`, `nix`, `git`, `gpg`, `omniwm`, `emacs-bridge`, `zsh`, `wezterm`, `fontconfig`, `jetbrains-fonts`, `macos`, `skhd`, `mcp`, `kotlin-lsp`, `ollama`, `confluence` — with brew first because the later tasks call what it installs. `hr` runs all sixteen. `compile-sources` byte-compiles every `.scm` under `src/` with `guild compile -W3`. Those are the only behaviours the repository can exercise.

The payloads are more varied than a dotfiles repository usually is. A Git configuration with an `includeIf` on `~/Work/` and a global gitignore, paged through `delta`. GPG. Homebrew taps, formulae and casks. A Nix profile. An OmniWM settings snapshot, which is a full generated TOML because OmniWM rejects incomplete files. A WezTerm configuration written in Lua from Scheme values — font, scrollback, opacity, blur, `window_decorations`, and a keymap whose Emacs chords are guarded by asking each pane which process is in front of it. A `.zshrc` assembled from `zsh.scm` data, a 564-line `shell-lib.zsh` spliced verbatim, and `notes.zsh`, which installs the `n` command. macOS `defaults` across Dock, Finder, trackpad and clock. An `skhd` keymap. MCP server definitions for three clients. A bridge file that Heks Emacs reads. Confluence Cloud mirrored weekly by a launchd agent, performed by a Python script driven through `uv`, Playwright and pandoc. And, newest, Ollama: the Homebrew service brought up, waited for on `localhost:11434`, and two models pulled if they are not already listed — `qwen3:8b` for tool calling, `qwen2.5-coder:7b` for code, both sized for a 16 GB laptop.

Five decisions constrain everything that follows.

1. **Data and mechanism are separate.** `prelude.scm` holds the serialisers — `mk-kv-conf-lines`, `serialize-rec-conf-item`, `css-conf-pair`, `install-config-file!`, `nix-profile-install` — and a module is mostly a data definition that names one of them. Adding a dotfile is meant to be a definition, not new file-mutation logic.
2. **Whole-file overwrite, not patching.** Idempotency comes from writing the file from scratch every time, which is also why the repository can claim byte-identical output. The cost is that a managed file cannot hold content a person added by hand, and no generated file can carry a "managed above this line" fence.
3. **Per-machine difference is a file, not a fork.** `load-local-overrides` lets `~/.config/cask-and-cons/<target>-settings.scm` layer on the shared base. `wezterm`, `macos`, `mcp` and `confluence` read one; `git`, `gpg`, `zsh` and `brew` do not.
4. **Secrets are named, never written.** An MCP header's value never reaches disk — the generated config references an environment variable, and a server whose variable is unset is skipped with a warning. The Confluence API token lives in the keychain. A generated file is therefore always safe to read and safe to publish.
5. **Two package managers, and only one of them is declared here.** The machine's software comes from Homebrew, declared in `brew.scm`. The *tools that do the declaring* come from Nix, pinned by `flake.lock` and by `nix-jointhefreeworld`, not declared in the modules at all. That split is recent and it is the most interesting structural fact in the repository: the provisioner is now bootstrapped by something other than itself.

Three limits are documented and worth keeping in view. The WezTerm key guard needs `pane:get_foreground_process_name()`, which only answers for local panes, so over `ssh` or inside the multiplexer the terminal keeps its own bindings. The Confluence mirror is flat per space, leaves `[drawio: ...]` placeholders where a diagram was, and fetches no attachments. And `install-omniwm` installs a snapshot of a settings file, which is why a `schemaVersion` bump means regenerating the whole file rather than editing a value.

The machinery around the modules is deliberately thin, and its gaps are visible. `sift` is in the profile and no task formats with it; `shellcheck` is in the profile and no task lints with it; `guile-veritas` is commented out of the profile because it fails to build on `aarch64-darwin`; there is no `test/` directory, no `check` task and no `NEWS.org`. The four sibling repositories in this collection all have the last three. This one has a compilation gate and no behavioural one.

## The vision

1. **A machine can be compared to its description without being touched.** `maak check` reports every managed file and `defaults` key that differs from what the modules declare, and exits non-zero; `maak hr` on a fresh macOS install still produces the same bytes. Today the second half is claimed and the first does not exist.
2. **Convergence is proven, not asserted.** Every payload renders to a string, that string is compared against a golden file, and rendering twice proves idempotency. The test suite becomes the reason the README's design section can stay short.
3. **Every machine in the collection shares one description.** Identity, prompt, pager keymap, Git, MCP and the editor bridge are the same on the Mac, on the Guix desktop and on the server, whichever shell each runs, because they are generated from one source with the platform as a parameter — not because three repositories keep byte-identical copies by hand.
4. **Every task can be undone.** Each target knows what it created, so `maak uninstall-<target>` exists, and a run that fails halfway leaves a machine whose state the tool can describe.
5. **The generated configuration stays the configuration a person would have written.** The Lua, the `.zshrc`, the plist and the JSON are readable on their own, and the diff between generated and hand-written stays empty — the point of generating them is that they are still yours to read.

## Features that are in scope and not built yet

The code already anticipates these; each is a seam the current design leaves open.

- **`maak check`.** The hard part is not the task but the comparator: `defaults read` returns typed values, and TOML, Lua and plists have no round-trip through the writer, so equality has to be defined per payload rather than as a string compare.
- **`maak test` and `maak fmt`.** `sift` and `guile-veritas` are already in the profile, which is most of the argument for both. What is missing is a `test/` tree and a decision about what a task that writes to `~/.zshrc` is allowed to assert.
- **`maak lint` over the shell.** `caco` is gone, but `shell-lib.zsh`, `notes.zsh` and `bootstrap` are shell, `shellcheck` is installed, and nothing runs it.
- **A plan/apply split.** `install-tasks` is a list of thunks that write as they go. A plan needs each module to describe its effects as data *before* performing them, which breaks the shape every module is built on.
- **Local overrides for `git`, `gpg`, `zsh` and `brew`.** The mechanism exists and four modules use it; the other four still require editing the repository for one machine's tweak.
- **One shared shell library instead of three copies.** `shell-lib.zsh`, `heks-bash/src/heks-bash/shell-lib.bash` and the `wolk-jjba` block are kept identical by hand, and `lesskey` is byte-identical across three repositories. Sharing them needs a released artefact the three repositories pin, not a fourth copy.
- **Confluence attachments and diagrams.** The sync leaves placeholders and fetches no images. The hard part is doing it on the same polite, serialised path — every fetch through the rate limiter, every storage-format reference rewritten to a local path — without turning a ten-minute sync into an hour.
- **The Confluence page tree as folders.** Flat per space is a deliberate simplification; a tree needs a move and rename strategy that does not rewrite a whole space when one page moves.
- **A changelog.** There is no `NEWS.org`; `git log` is the only history a user of this repository has.
- **A guard on what a task may touch.** Nothing today prevents a task from writing outside the paths its name suggests. A declared target list per module — the files and `defaults` domains a task owns — would turn `hr` from sixteen tasks in a row into a plan whose overlap can be checked before it runs.
- **`install-ollama` as a convergence rather than a pull.** It is the first target whose "file" is another program's running state: a service to bring up, a list to compare, models to fetch that may be tens of gigabytes. Deciding what `--check` means when the state is a daemon's — versions, digests, disk — is the first genuinely new design question the install tasks have posed since `defaults`.

## New features that would be worth having

- **`maak render <target>`** — print the payload instead of installing it. The smallest feature that makes golden tests possible and lets a reader diff a change before trusting it.
- **`maak doctor`** — check the prerequisites the README documents by hand: Nix, Homebrew, Guile, `uv`, pandoc, Chrome, the launchd agent actually loaded, the OmniWM file matching the installed `schemaVersion`, Ollama answering on its port. A table, with versions.
- **The tools in the modules, not only in the flake.** `flake.nix` is the second place to look for what this machine needs, and it is written in a different language from everything else. A `tools.scm` that declares the same list, with the flake generated from it, would make one language the whole description.
- **Declared secret locations.** The design already refuses to write tokens; the next step is a form like `(secret . (NAME . "keychain:service"))` that says where each value is read from and which tasks need it before they run.
- **An inventory of what the machine has.** `brew.scm` declares formulae and casks and `ollama.scm` declares models; recording the *installed* sets and diffing them against the declared ones answers the question the declarative model cannot answer today: what is on this machine that the repository does not know about.
- **Revertible `defaults`.** Read each managed key before writing it, keep it, and let `maak install-macos --revert` put it back. The module already computes which keys differ; it throws that information away.
- **A machine identity record.** Flavour, host kind, sigil, accent and rc file already exist in three places. One record, printed by `about` on every shell, would make "all my machines feel like one" a data structure rather than a convention.
- **A model policy with a memory budget.** `ollama-models` is a list chosen for 16 GB. Declaring the budget, the models and what each is for — tool calling, code, prose — and refusing a set that does not fit would make the module the machine's AI configuration rather than a pull list, and it is the natural companion to the MCP servers the same repository already writes.
- **A `maak diff <target>` that shows the change, not the file.** For the small payloads the useful review is a unified diff against what is on disk, with the file's own path in the header.
- **A generated README section for the task list.** `maak.scm`'s exports are the authority; the README's list is a copy kept correct by hand. Printing it from the module is the trick Heks Emacs uses for its keybindings reference, and it removes an error class this repository has already met.
- **A stamp from the last successful `hr`.** A date written on success, printed by `about`, is the cheapest possible reminder that the description and the machine have parted company.
- **A `maak explain <task>` that prints what it will touch.** The modules know: `git.scm` exports `gitconfig-filename`, `zsh.scm` names `~/.zshrc` and the lesskey path, `confluence.scm` names the plist and the log. Collecting those into a line per task is a small amount of data and the beginning of an answer to "what does `hr` actually do to my machine".
- **A weekly summary from the Confluence log.** The sync already counts pages new, changed, removed and unchanged, macros it did not understand and pages that failed to convert. Appending that summary under the mirror turns a launchd log nobody reads into a record of the archive's growth.
- **`maak install-zsh --diff`.** The shell half is where a change is most visible and least reversible; showing the unified diff against the installed `~/.zshrc` before writing it is a small feature with a large effect on how willing a person is to run it.

## Contributions that would move the needle

Ranked roughly by value per hour. The first three are afternoons; the last three are projects.

1. **Golden-file tests for the serialisers.** Highest value for the least work: every payload is already a pure function from data to a string, so the test is a directory of expected outputs and a loop over the modules. It makes the idempotency claim testable and catches the silent breakage a formatting change in `prelude.scm` causes across fifteen modules at once.
2. **`maak fmt` and `maak lint`.** `sift` and `shellcheck` are installed by the bootstrap already; the tasks that call them are ten lines each, and they turn two profile entries into a convention.
3. **`maak render`, and `maak check` for `install-git` and `install-zsh` first.** Both payloads are plain text with no round-trip problem, so equality is a string compare. A day's work that establishes the pattern for the thirteen harder targets.
4. **Local overrides for the four modules without them.** The mechanism exists and is used; extending it is mostly a data definition, and it removes the last reason to edit the repository for one machine.
5. **A `NEWS.org`.** Small and unglamorous, and it makes every release above legible to a reader who wants to know what changed on their machine.
6. **The `n`/Emacs format contract as a test.** Rendering both writers' index pages for the same notes tree and diffing them is a small test with a large claim behind it, and the only way the byte-identical promise survives a change on either side.
7. **Confluence attachments.** Valuable and the most work: Playwright sessions, the rate limiter, and storage-format rewriting.
8. **A regression check for the generated WezTerm file.** Rendering the Lua and asserting the chord table, the guard list and the decoration value would catch the class of change that currently only a person notices.
9. **`tools.scm`, and the flake generated from it.** Larger than it sounds, because it makes the bootstrap chain one language, and it is the change that would most reduce what a new contributor has to learn to answer "what does this machine need".
10. **A `NEWS.org` entry per release, and the release task that cuts one.** The sibling repositories have both; here a release is a commit message, so the history a user reads is whatever `git log` happens to say.

## Compared to related projects

| Project | What it is | Where cask-and-cons differs |
|---|---|---|
| GNU Guix Home | Declarative home-environment configuration in Guile Scheme, over a daemon, a store and a full package manager | The closest relative in language and philosophy, and it reaches further: packages, services, rollback. `cask-and-cons` runs without a daemon, targets macOS first — where Guix does not run natively — and leaves packages to Homebrew |
| Nix Home Manager | Declarative user configuration for Nix, with a module system and a store | Needs Nix and its module language. `cask-and-cons` now uses Nix for its own tools, so this neighbour is nearer than it was, but the payloads stay ordinary files written by an ordinary Guile process |
| nix-darwin | NixOS-like declarative system configuration for macOS, including `defaults` and launchd | Both write `defaults` and activate agents. `cask-and-cons` converges only the keys that differ, restarts only the processes affected, and generates the terminal, prompt and MCP configurations nix-darwin has no opinion about |
| chezmoi | Dotfile manager with templates, secrets and a fleet of machines | chezmoi templates files; this generates them from a data structure through a per-format serialiser, so a Git configuration is an alist rather than a template full of conditionals |
| yadm, GNU Stow | Git-tracked dotfiles, symlinked into place | Both answer *where* a file lives; the content stays yours to keep in sync by hand, so a machine-specific value becomes a branch or a copy |
| Ansible, Puppet | Declarative configuration management for fleets, over SSH or an agent | Built for many machines with a YAML inventory and a runtime to install first; this is for one person's laptop, and its playbook is a Scheme module |
| Homebrew Bundle | A `Brewfile` of formulae, casks and Mac App Store apps, applied with `brew bundle` | A `Brewfile` is declarative package state and nothing else, which is the half `install-brew` covers; this adds the configuration those packages then read |
| `mathiasbynens/dotfiles` and the `defaults write` scripts around it | A long, popular shell script of `defaults write` calls | Those scripts are imperative, unverified and silent about what they overwrite. `install-macos` diffs first, writes only what differs, and knows which process each domain belongs to |
| Mackup | Copies application settings in and out of a synced folder as a backup | A backup, not a converged state: with no desired content, the file is whatever it was last synced to |

The others do three things this project could still add. chezmoi's willingness to let generated and hand-written content share a file is the answer to the whole-file-overwrite cost, and a fence marker is cheap. Guix Home's plan/apply and rollback are the shape a provisioner is expected to have. Ansible's separation of inventory from recipe is what "three machines, one description" really means, and this repository is halfway there through `load-local-overrides`.

What none of them offer, and what the newest module in this repository begins to need, is a description of a machine that includes the programs which are not files: a daemon and its data. `ollama.scm` pulls models; `install-confluence` loads a launchd agent; `install-mcp` decides which servers exist at all, because an unset variable removes one. A neighbouring project would model those as services with states; this one models them as side effects of a task, which is honest, readable, and the next thing that has to change.

Where `cask-and-cons` is ahead and should stay ahead: per-format serialisers rather than heredocs, so the desired state is inspectable and diffable as data; secret indirection in the MCP generator, which makes a generated configuration safe to commit and safe to publish; honesty about which processes a change restarts; and the refusal to treat the terminal, the prompt, the pager, the editor bridge, the local models and the notes format as separate concerns.

One thing none of the others do, and this project already does, is worth defending: it ships the generator and the data together, in a language the reader is expected to read. A `Brewfile`, an Ansible role and a chezmoi template are all consumed by something the reader did not write. Here `macos.scm` is the answer to "why is my Dock like that", and `ollama.scm` is the answer to "why are these two models on this laptop".

## In the long run

- **One description across two operating systems.** macOS and Guix are the two machines that matter; identity, the shell library, the pager keymap, Git and the MCP definitions are the same on both. The bet is that the platform disappears into a parameter and `about` becomes a query rather than a comparison between repositories.
- **A machine as a build artefact.** With golden tests, a check mode and a bootstrap that is now a script rather than a paragraph of README, provisioning stops being a ritual performed with care and becomes something that either converges or fails loudly. That is the difference between dotfiles and a system definition.
- **The tools in one language.** `maak.scm`, `flake.nix` and `bootstrap` are three languages and three levels of the same dependency question. The long bet is that the flake becomes generated output of a Scheme declaration, and a contributor needs only one file to know what this machine needs.
- **The notes format as an interchange.** `n` already writes index pages byte-identical to the ones Emacs writes, and moving a note is deliberately left to Emacs because it has to repair the links. Extending that contract to every file, with a test that renders both sides and diffs them, would make the format a specification two implementations agree on.
- **The local model as part of the machine.** Two models pulled and an MCP configuration written by the same repository is the beginning of a laptop that describes its own AI: which servers, which models, which token scopes, and what each one is allowed to reach. The bet is that this becomes as ordinary a part of a machine description as the shell prompt.
- **The Confluence mirror as an archive.** A read-only weekly copy that is exact — deletions propagate, a `.git` directory in the destination is preserved — is a backup. The bet is that the archive outlives the tool, because it is plain Markdown with front matter and nothing else.
- **A bootstrap that is one command on a machine with nothing.** Today it is Nix first, then `./bootstrap`, then `maak hr`, and the README explains the order. The bet is that the order stops mattering: the profile, the formulae and the files converge from a single entry point, and a machine that has only a network and a shell can become this machine.

## A closing note

This document exists because the decisions that matter here are invisible from the README: that a file is overwritten rather than patched, that a secret is a name rather than a value, that the shell, the pager, the local models and the Dock are the same configuration. Written down, they are easier to keep and easier to argue with.

The order above is deliberate. `fmt`, `lint`, `render` and `check` come first because everything else becomes reviewable once the machine can be compared to its description: an inventory, revertible `defaults` and a model budget all turn into diffs in a repository whose diffs are already the point. The generated payloads — the Lua, the `.zshrc`, the plist — are the part most likely to surprise a reader, so they are the part with the strongest reason to carry a golden file.

*This document describes intent, not commitments: it names directions the maintainer finds worth taking, and nothing here is a promise that a given feature will exist, in the order listed, or at all.*
